## D1 — JSON numbers parsed as strings: **CONFIRMED (independently)**

Source-level:
- `src/foundation/Json.cpp` `Parser::parseNumber` ends with
  `out = JsonValue(text.substr(start, pos - start));` — the `std::string` overload.
- `src/foundation/Json.h:25` `explicit JsonValue(std::string s) : type_(Type::String) …`
  sets **String**, so every parsed number is mistyped.
- `JsonValue::asDouble/asInt64` return the fallback when `type_ != Type::Number`.

My **own** probe against the real classes (independent of Agent-C's):

```
$ g++ -std=c++17 -I src /tmp/probe.cpp src/foundation/Json.cpp -o /tmp/probe && /tmp/probe
parse ok=1 err=
open: isNumber=0 isString=1 asDouble=-1.000000 asString=4076.56
n:    isNumber=0 asInt64=-1
```

`parseNumber` is the **only** producer of `Type::Number` from wire text, so this is
not the intended "keep numbers as text" behaviour — the type metadata is simply never
set. (`Json.h` comment: "Numbers are kept as text to preserve integer precision" — the
implementation defeats that by labelling them String.)

**Blast radius (my assessment):** every `asDouble`/`asInt64` on a **parsed** document
returns its fallback (often 0). Only documents built via constructors/dumps are typed
correctly. This affects any real-bridge ingest *and* any parsed request/config body —
it is latent only because committed fixtures are generated by `mock_api.py` and
written via `dumpInto`/`asString`. Agent-C's "invisible on the synthetic path, surfaces
on real ingest" framing is correct.

- **`src/` is pristine** at HEAD: `git status --porcelain src/` is empty — Agent-C's
  temporary patch was reverted as claimed, and the default T13 suite is still 52/52.
- **Suggested fix direction is sound** (construct numbers with `Type::Number`, e.g. a
  numeric factory). The fix itself belongs to the foundation owner; I did not apply it.
